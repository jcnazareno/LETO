# LETO: Lunar Event-camera Transient Observatory

LETO is a student mission-design project for the *Space Mission Design* course at the Chair of Spacecraft
Systems, TUM (AY 2026-2027). The team is taking a lunar impact-flash mission from ECSS **Phase A**
(feasibility) into **Phase B** (preliminary definition). The System Requirements Review (SRR) was submitted on
20 November 2026.

The mission idea in one paragraph: a single micro/mini-class spacecraft first spends about 2.5 years in a high
lunar orbit (about 3000-7000 km) watching the whole night side of the Moon with several event-camera heads
(Sony IMX636), detecting meteoroid impact flashes. It then lowers its orbit to about 160-350 km and images the
flash sites at 1 m pixel scale or better, so that each flash can be paired with the fresh crater it made. The
goal is at least 30 (and ideally 80) verified flash-crater pairs, to calibrate how flash energy relates to
crater size.

This is mostly a **document and analysis repository**: reports, budgets, trade studies, and the Python/GMAT
simulations behind them. There is no single build or test command.

> **Authoritative source:** the requirements live in
> [`00_OrganizationalMatters/LETO_SystemRequirementsReport/LETO__SRR.pdf`](00_OrganizationalMatters/LETO_SystemRequirementsReport/LETO__SRR.pdf).
> If another document disagrees with the SRR, the SRR wins until the team changes it.

If you are an AI coding agent, also read [`AGENTS.md`](AGENTS.md).

## Existing simulations and tools

Most tools follow the same layout inside their folder:

| Subfolder   | What goes there |
|-------------|-----------------|
| `analysis/` | The code (Python scripts, GMAT generators) and a `README.md` with install and run commands |
| `data/`     | Input data and generated data files that are small enough to commit |
| `outputs/`  | Results: Markdown reports, interactive HTML pages, videos, workbooks |
| `figures/`  | Plots generated by the scripts |

The `.html` pages are self-contained. Download them and open them in a browser to explore the results without
running anything.

### Payload (`02_SubSystems/01_Payload/`)

| Tool | What it does | Start here |
|------|--------------|------------|
| **Event-stream simulator** (`event_stream_simulator/`) | Simulates the event stream of one IMX636/IMX646 camera head looking at a real, drifting lunar scene (WAC albedo and LOLA terrain), including readout, on-chip filters, radiation particles (from CRaTER), hot pixels, stars and stray light. Runs the on-board flash trigger and the event-only energy estimate on the result, with validation cases V1-V10, a pointing-jitter sweep and pixel-sensitivity studies. Python (NumPy, SciPy, Numba). | [`README.md`](02_SubSystems/01_Payload/event_stream_simulator/README.md), then [`analysis/event_stream_sim/README.md`](02_SubSystems/01_Payload/event_stream_simulator/analysis/event_stream_sim/README.md) for commands. Results in `outputs/event_stream_sim.md` and `outputs/event_stream_sim.html`. |
| **Flash-response pixel model** (`event_stream_simulator/analysis/flash_response/`) | The small 4 × 4 pixel model (study "S10") that the full simulator extends. | `event_response.py` |
| **Sensor trade** (`sensor_trade/`) | IMX636 vs. IMX646, cooling need and number of camera heads. | [`sensor_trade.md`](02_SubSystems/01_Payload/sensor_trade/sensor_trade.md) / `.pdf` |
| **Simulation explorer** (`simulation_explorer/`) | Report and interactive page covering the screening simulations behind the original mission proposal (revision 5): yields, detection, orbits. | `simulation_summary.md` (short), `simulation.md` (full), `simulation_explorer.html` |
| **Orbit trade explorer** (`orbit_trade_explorer/`) | Interactive comparison of monitoring-orbit options. The same file is also in `09_MissionAnalysis/`. | `orbit_trade_explorer.html` |

### Structure (`02_SubSystems/05_Structure/`)

- `pbsStructuresDraft.xlsx`: draft product breakdown structure (PBS) for the structure subsystem.
- `subSystemRequirementsStructures.xlsx`: draft structure subsystem requirements, mapped to the PBS.

### Mission analysis (`02_SubSystems/09_MissionAnalysis/`)

| Tool | What it does | Start here |
|------|--------------|------------|
| **GMAT lunar setup** (`gmat_lunar_setup/`) | Python generator that writes GMAT R2026a scripts for the lunar mission (Option A: 3000 km monitoring / 300 km imaging), plus a validation suite and summary tools. Recorded scripts and run histories are in `outputs/`. Needs a local GMAT R2026a install for new runs. | [`README.md`](02_SubSystems/09_MissionAnalysis/gmat_lunar_setup/README.md), [`outputs/ASSUMPTIONS.md`](02_SubSystems/09_MissionAnalysis/gmat_lunar_setup/outputs/ASSUMPTIONS.md), editable `analysis/gmat_lunar_setup/config.json` |
| **Supporting studies** (`supporting_studies/`) | Concept-level studies done before the SRR, each with its own `analysis/<study>/README.md` and dated `outputs/<study>_<date>/` folder. | [`README.md`](02_SubSystems/09_MissionAnalysis/supporting_studies/README.md) and `studies_explorer.html` |
| **Orbit trade explorer** (`orbit_trade_explorer/`) | Same page as in Payload. | `orbit_trade_explorer.html` |

The supporting studies are:

- **Radiation environment** (`radiation_environment_research`): lunar-orbit radiation and its effect on the
  sensors and electronics.
- **Orbit and attitude disturbances** (`disturbance_environment_research`): perturbations and disturbance
  torques for the concept orbits. Has its own `requirements.txt`.
- **LUMIO comparison** (`lumio_comparison_research`): how LETO compares with ESA's LUMIO CubeSat.
- **D01-D04 flash photon budget** (`d01_d04_research`): flash light curves, signal budget and impact energies,
  built on a compilation of 192 validated NELIOTA flashes.
- **Crater-injection test** (`crater_injection_test`): how often the crater camera would find and measure a
  fresh crater by comparing new images with archived LROC NAC "before" images. Follow-up with real new craters
  in `outputs/lroc_lola_update/`.
- **Flash-crater models** (`analysis/flash_crater_models/`): the joint flash-to-crater yield model and lunar
  texture models used by the studies above.
- **Studies explorer** (`analysis/studies_explorer/`): builds the interactive `studies_explorer.html`.

## Large external datasets (not in the repo)

Several tools read large NASA datasets that are **not committed**. Any folder called `data/external/` is ignored
by git (see [`.gitignore`](.gitignore)). Download the data yourself and place it there, or point the tools at it
with the environment variables listed in each tool's README.

| Dataset | Used by | Expected location |
|---------|---------|-------------------|
| LRO WAC Hapke-normalised 643 nm albedo tiles | Event-stream simulator | `event_stream_simulator/data/external/ALBEDO_WAC_HAPKE_NORMALIZED_REFLECTANCE_643NM/` (or `EVENTSIM_WAC_DIR`) |
| LOLA LDEM_64 elevation model (`ldem_64.img`) | Event-stream simulator, crater studies | `.../data/external/LOLA_DATA/` (or `EVENTSIM_LOLA_DIR` / `EVENTSIM_LOLA_FULL`) |
| LRO CRaTER PRI/SEC particle files (raw) | Event-stream simulator (the reduced days are committed in `data/crater/`) | `.../data/external/CRATER/` |
| BSC5 bright-star catalogue | Event-stream simulator (star runs) | `.../data/external/BSC5/` |
| LROC NAC CDR images and new-crater catalogue | Crater-injection test, real-crater follow-up | `supporting_studies/data/external/NAC_CDR/` |

The exact file names and versions are listed in the README of the tool that uses them. Recorded outputs are
committed, so you can read the results without downloading anything; you only need the datasets to rerun.

**Never commit these datasets.** The repository is already large (several hundred MB of history), mostly from
outputs and videos. If you produce large intermediate files, keep them in a `data/external/` or `tmp/` folder
that git ignores.

## Where to put things

| You have... | Put it in |
|-------------|-----------|
| A course deliverable (SRR, later reviews, presentations) or admin document | `00_OrganizationalMatters/LETO_<DeliverableName>/` |
| A paper, lecture, datasheet or other document the team did not write | `01_ExternalResources/` in the matching `AA_`, `AB_`, ... folder, or a new `AC_<Topic>/` folder |
| A budget, trade study, requirement list or report for one subsystem | `02_SubSystems/NN_<Subsystem>/` |
| Analysis code for a subsystem | `02_SubSystems/NN_<Subsystem>/<tool_name>/analysis/`, with a `README.md` (inputs, outputs, how to run) and pinned dependencies (`requirements.txt`) |
| Results of that code | The same tool's `outputs/` (reports, HTML, workbooks) and `figures/` (plots) |
| Small input data (under a few MB) needed to rerun | The same tool's `data/` |
| Large downloaded datasets | The tool's `data/external/` (ignored by git) |
| Orbit, delta-v, eclipse or environment analysis | `02_SubSystems/09_MissionAnalysis/` |
| Mode diagram and operations concept for both mission phases | `02_SubSystems/12_ConOps/` |
| Work that spans several subsystems (system budgets, PBS) | The subsystem that owns the main driver, with a link from the others, or ask the team before adding a new top-level folder |

### Conventions

- **Numbered prefixes** (`00_`, `01_`, `02_` and `AA_`, `AB_`) keep folders in order. Add new folders at the end
  instead of renumbering existing ones.
- **Folder names** use PascalCase with no spaces (for example `OnBoardDataHandling`). Tool folders inside a
  subsystem use `snake_case` (for example `event_stream_simulator`). External files keep their original titles.
- **Remove the `.gitkeep`** from a subsystem folder once it has real content.
- **Requirement IDs** follow the SRR: `STK-`, `MO-`, `MSC-`, `MR-`, `SYS-`. Subsystem requirements get their own
  prefix (for example `PL-`, `TH-`, `PWR-`, `PROP-`, `STR-`, `ADCS-`, `COM-`, `OBDH-`) and trace to a parent
  `SYS-` or `MR-` ID.
- **Open values** are tagged `[TBD]` (to be determined) or `[TBR]` (to be reviewed) until the team closes them.
- **Margins** follow ESA practice as in the SRR: equipment maturity margins plus a 20 % system margin on dry
  mass and power. State the source of every budget line (datasheet, analogy, scaling).
- **SI units** throughout, **IEEE-style references** with DOIs.
- **Commit editable sources** (Markdown, LaTeX, spreadsheets, scripts) next to any exported PDF.
- Do not edit or reformat files in `01_ExternalResources/`.

## Working together

- `main` holds the agreed baseline. Do your work on a branch and open a pull request for review.
- Dated folder names (for example `radiation_environment_research_2026-10-29`) record when a result was
  produced. When you rerun a study with changed assumptions, create a new dated output instead of silently
  overwriting the old one.
